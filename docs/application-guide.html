Android app · Flutter · Material 3

Remove watermarks from a PDF, on the phone itself.

You choose a PDF. The app copies it into its own private storage, finds the watermark, lets you mark the area if needed, removes it with a Python engine that is packaged inside the APK, checks every page against the original, and saves a cleaned copy where you choose. The file never leaves the phone and the app has no network permission.

Android 7+, 64-bit ARM Works offline No network permission Original never modified 41.6 MB APK

User interface

Flutter 3.50 with Material 3 components, following five Figma frames. Newsreader headlines, Figtree text.

Processing

A Python 3.13 engine (pypdf, PDFium, Pillow) embedded with Chaquopy and called from Kotlin. Same process as the app.

Current status

APK built and inspected, automated tests pass. Not yet run on a real phone. The in-app “Check PDF engine” action is the first thing to try.

Purpose and scope

One job: a clean copy, or a clear refusal

The app is for people who hold a PDF with a watermark on it and need a copy without it. It removes what it can identify and prove safe. When it cannot, it says so and produces nothing, instead of guessing.

What it removes

  • Watermark annotations: objects whose PDF subtype is /Watermark.
  • Acrobat-style watermark layers: page content marked /Artifact with subtype /Watermark, on every page.
  • Anything inside an area you mark: text, images and vector shapes that lie fully inside your rectangle on page 1, applied to every page or only to page 1. /Watermark and /Stamp annotations fully inside are removed too.

What it does not remove

  • Password-protected PDFs (the engine does not decrypt) and digitally signed or certified PDFs (it refuses to modify them).
  • A watermark that is part of a scanned page image: there is no separate object to remove.
  • Objects only partly inside the area you marked. They are kept on purpose.
  • Watermark layers nested inside form objects, or split across content streams. Those pages are reported and left unchanged.

Principles that shaped every decision

  • Never touch the original. The engine reads a private copy and writes a separate file.
  • Prove it before publishing. Every page is rendered before and after. A change outside the removed area means no output file.
  • Refuse instead of guess. Unsupported structures produce an explicit outcome and a code, never a silently altered PDF.
  • Keep the file on the phone. No upload, no account, no server.

How it was planned

From a front end and a lab engine to one installable app

The project began as two separate pieces that were never connected. The plan was to join them, make the engine useful on real documents, match the Figma design, and then move all processing onto the phone when that became the requirement.

  1. Stages 1 to 5 · first repository

    Front end only

    Home, Upload and Processing screens from the Figma design; PDF picking and validation; a first-page preview; manual selection of a watermark area kept in memory. Processing stayed at “Not started”.

  2. Stage 6A · verified 14 November 2026

    A strict, separate Python engine

    Removed only explicit /Watermark annotations, in a resource-limited worker process, with independent PDFium checks. 66 tests. Not connected to the app.

  3. 18 November 2026 · review

    What was missing, found by reading and running the code

    The app called nothing; the server could not start (four separate import and configuration faults); a rendering package was used but not declared; and the engine’s scope was too narrow for real files, because most watermarks are page content, not annotations.

  4. 18 November 2026 · scope decision

    Extend the engine

    Add Acrobat-style artifact removal and removal by marked area, both verified by rendering.

  5. 18 November 2026 · design pass

    Figma frames, Material 3, new fonts

    Five frames implemented from the prototype, mapped onto a Material 3 theme; Material components added beside the design; Inter replaced by Newsreader and Figtree.

  6. 18 November 2026 · requirement change

    Processing moves onto the phone

    A first version sent the PDF to a server on a PC and worked in tests, but a phone without that server saw “Server not reachable”. The requirement was local processing, so the engine now runs inside the APK and the server was deleted.

  7. Now

    APK 1.1.0 built, device test pending

    Flutter and engine tests pass; the packaged Python and PDFium have not yet been seen starting on a phone.

What happens inside

One request, from tap to saved file

Dart and Python never share memory. They share a folder. The channel between them carries only short JSON strings, and every large file stays on disk.

Where files live

cache/pdfwm/jobs/<uuid>/
  original.pdf   private copy of the pick
  preview.png    page 1, rendered by PDFium
  state.json     hash + geometry digest + job
  processed.pdf  the cleaned copy
  result.png     page 1 of the cleaned copy
  work/pdfwm_*/  engine scratch, auto-deleted

Closing a document deletes its folder. Folders older than one hour are purged the next time the engine starts.

Threads

Dart UI
Draws screens, handles touches, streams the file copy. Never waits on Python.
Platform thread
Receives channel calls and posts replies.
Executor thread
One background thread runs every Python call, so documents are processed one at a time.

Python runs in the app’s own process through Chaquopy; there is no separate service.

The removal engine

Edit narrowly, then prove nothing else changed

The engine is the part with no room for error, because a wrong edit silently damages someone’s document. Everything is built around making that visible before a file is produced.

Automatic mode

Removes supported /Watermark annotations (an explicit structural type, never inferred from text or position) and Acrobat-style artifacts, where all objects of a watermark on a page are removed together or the page is left alone.

Area mode

Your rectangle on page 1 is mapped to each page’s own crop box and rotation. Every object fully inside it is removed, with a half-point tolerance. Partial overlaps are kept. Text is kept if removing it would move later text on the same line.

The pipeline

  1. Snapshot

    Copy the input into a private scratch folder while hashing it. A later change to the source fails the job.

  2. Strict parse

    Check header and end marker, object graph, page boxes, rotations and stream sizes against limits. Encrypted files stop here.

  3. Scan

    Find annotations and artifact sections; render every page once as a baseline.

  4. Edit

    Remove annotation references, or splice out only the painting operator of each removed object. Every other byte stays identical.

  5. Verify

    Reopen strictly and with PDFium. Compare geometry, then pixels and text outside the removed area. Check counts add up.

  6. Publish

    Re-hash the source, then create the output exclusively. A hard link is tried first; on phones a rename is the fallback.

What “verified” means here

  • Page count, boxes and rotation of every page are unchanged.
  • Every page, rendered at 1,024 px on its long edge, is pixel-identical outside the removed objects’ bounds (plus a 2 px margin).
  • Characters outside the removed area are unchanged.
  • The number removed equals the sum by kind and the pages changed match.
  • The source file’s hash is the same after processing as before.

A failed check returns processing_failed with a specific code. Nothing is published. Checks run at 1,024 px and do not prove identical rendering in every viewer.

Outcomes

watermark_removed_successfullyA cleaned file exists and passed every check.
no_supported_watermark_detectedNothing removable in scope. No file. Not proof the PDF has no watermark.
unsupported_watermark_structureA candidate or document the engine will not edit (for example, signed).

invalid_or_unreadable_pdfCannot be opened or fails structural checks.

Why these choices

The decisions, and what each one costs

Each card gives the decision, the reason, what was rejected, and the price paid. Where a choice was forced by a limit of a platform or a library, the limit is named.

Interface

Flutter with Material 3

One Dart code base, exact control over drawing and touch for the selection rectangle, and Material 3 components built in. The project began in Flutter and the Figma design maps onto it directly.

Rejected: a native Kotlin interface. It would also work; nothing needed it enough to justify restarting.

Cost: a bridge to Kotlin and Python, and a larger APK.

Engine language

Keep the engine in Python

It already existed, with a strict design and 66 tests, and PDF repair work needs mature parsing code. pypdf gives full access to the object graph; Dart has no comparable package.

Rejected: porting to Kotlin or Dart. Months of work to re-earn the same trust, with new bugs in the one place bugs are unaffordable.

Cost: an embedded interpreter.

Packaging

Embed Python with Chaquopy

It puts CPython and pip-installed wheels inside the APK and lets Kotlin call Python directly. pypdf is pure Python, pypdfium2 has an Android wheel, and Pillow has a Chaquopy build.

Rejected: a PC server (the earlier design, removed). Also rejected: other Python-on-Android toolchains, which do not embed into an existing Flutter app as directly.

Cost: arm64 only (Python 3.13 and pypdfium2 have no 32-bit or x86 build here), about 25 MB added.

Execution

Run the engine inside the app process

Android cannot start a second Python interpreter, so the worker-process mode used on a PC is not available. An in-process mode runs the same code and the same checks.

Cost: no memory cap and no hard time limit. The adapter compensates with lower input limits (40 MiB, 100 pages) shown to the user before a file is accepted. A runaway document could still stop the app.

Libraries

pypdf for structure, PDFium for pixels

Two independent implementations. pypdf proves the object graph is unchanged; PDFium proves what a viewer would draw is unchanged. Agreement of both is the evidence.

Rejected: PyMuPDF (AGPL), pikepdf/qpdf (viable, but no renderer and a heavier native footprint).

Editing

Splice bytes; do not regenerate content

PDFium can rewrite a page’s content stream after objects are removed. In testing it dropped shading and inline images, lost character and word spacing, and leaked text render mode into later text. The engine instead removes only each object’s painting operator and leaves every other byte alone.

Cost: its own content-stream reader (the largest module, 702 lines) and some structures it deliberately skips.

Safety

Verify by rendering; fail closed

A PDF can be structurally valid and visibly wrong. Rendering before and after is the one check that matches what a person sees.

Cost: time (every page is rendered twice) and a small chance of refusing a good edit. Both are accepted: a refusal is cheap, a corrupted document is not.

Coordinates

The engine renders the preview you draw on

Rectangles are stored as 0 to 1 fractions of the engine’s own page-one image, bound to that exact preview by a hash of the page geometry. There is no guessing between screen pixels, an Android renderer and PDF units, especially on rotated or cropped pages. An earlier version rendered the preview with a separate Android library; that was removed.

Data flow

Files on disk, JSON on the channel

PDFs can be tens of megabytes. Passing them through a platform channel copies them several times in memory. A per-document folder keeps the channel small and makes cleanup one delete.

Concurrency

One document at a time

One executor thread serialises engine calls. It protects memory, and the app only ever works on the document on screen.

Originals

Work on a copy; publish exclusively

The source is never opened for writing, outputs are created with a flag that fails if the file exists, and the source is re-hashed afterwards. The user’s file cannot be lost to a bug here.

Why local processing

The file stays where it is

The first complete version used a server. It passed its tests, and it still failed the one test that mattered: install the app on a phone and use it. Moving the engine into the app removes the edge that failed.

What local processing gives

  • Privacy. Contracts, scans and invoices never leave the phone. The release manifest has no internet permission, so this is enforced by Android rather than promised.
  • It works anywhere. No Wi-Fi, no PC, no setup screen, no address to type.
  • Nothing to run or secure. No hosting, accounts, tokens, rate limits or expiry jobs. A public upload service would need all of them, and sandboxing for a native PDF parser.
  • No upload wait. A 40 MB file never crosses a network.

What it costs

  • A bigger app. 41.6 MB, because Python, PDFium and Pillow ship inside it.
  • Phone-sized limits. 40 MiB and 100 pages, and speed that depends on the phone.
  • Less isolation. No separate process, memory cap or hard timeout (see Limits).
  • arm64 phones only. That covers nearly all phones sold in the last several years, but not every device.
  • Updates need a new app version. The engine cannot be patched on a server.

Limits and next steps

Known risks, in the order they matter

1. Not yet run on a device

Likeliest failures are PDFium or Pillow not loading in the packaged app. First step: install the APK and run Check PDF engine. An emulator test needs an x86_64 PDFium build that does not exist on PyPI and would have to be built.

2. In-process risk

A very large or hostile PDF could exhaust memory or run long inside the app. Limits are enforced before processing, not during. If this proves real, move the engine into a separate Android service process with its own memory ceiling.

3. Scope of removal

Watermarks inside scanned images, nested forms or encrypted files are out of reach. The app says so instead of guessing. Real-world coverage is the main measure of usefulness still to be taken.

4. Distribution

The APK is signed with the debug key and uses the placeholder ID com.example.pdf_watermark_remover. A real release key and ID are needed before any store listing.

5. Library versions

Pillow differs between the phone (11.0.0) and the PC tests (12.3.0). The engine uses only functions common to both, but a phone-side run of the full engine suite would close the gap. PDFium and pypdf need security updates tracked.

6. Platforms

Android only, arm64 only. The iOS, desktop and web folders were removed; they can be regenerated with flutter create if needed, but the engine packaging is Android-specific.
